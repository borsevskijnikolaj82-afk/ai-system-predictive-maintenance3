# Лабораторная работа №3 — Реализация программного компонента системы искусственного интеллекта

## 1. Тема и реализованный компонент

Тема проекта — Predictive Maintenance для оборудования.

Реализован изолированный компонент оценки риска технического состояния оборудования. Он принимает телеметрию, проверяет входной контракт, подготавливает признаки, выполняет интеллектуальную оценку риска и применяет правило передачи результата на ручную проверку.

## 2. Место компонента в архитектуре ЛР2

В ЛР2 использован модульный монолит:

Клиент → FastAPI → PredictionService → preprocessing → ModelLoader/AI model → PredictionRepository.

В ЛР3 реализован автономный фрагмент:

PredictionRequest → validation → preprocessing → RiskBaselineModel → business rule → PredictionResult.

Компонент не требует FastAPI, базы данных или внешнего API. Это позволяет запускать тесты без веб-сервера и сети.

## 3. Входной и выходной контракт

| Поле | Тип | Ограничения |
|---|---|---|
| item_id | str | 1–128 символов |
| temperature | float | -50…250 °C |
| vibration_amplitude | float | 0…100 мм/с |
| operating_hours | int | >= 0 |
| error_code_last_24h | int | 0…999 |

Выход содержит prediction, probability, model_version и manual_review_required. Дополнительные неизвестные входные поля запрещены.

## 4. Интеллектуальная функция

Вместо большого обученного файла модели используется компактный воспроизводимый baseline-алгоритм, что допускается методическими указаниями ЛР3.

Risk score рассчитывается как:

0.003 × max(temperature − 70, 0)
+ 0.05 × vibration
+ 0.00005 × operating_hours
+ 0.01 × error_code,

после чего ограничивается диапазоном 0…1.

Классификация:
- risk < 0.45 — NORMAL;
- 0.45 <= risk < 0.75 — WARNING_ANOMALY;
- risk >= 0.75 — CRITICAL_RISK.

Интеллектуальная функция находится в app/inference.py, подготовка признаков — в app/preprocessing.py.

Значение probability в данном компоненте является risk score, а не калиброванной вероятностью отказа.

## 5. Прикладное правило

В app/service.py модельный результат отделён от прикладного решения.

Если risk score меньше порога 0.8, устанавливается manual_review_required=true. Таким образом, модель отвечает за оценку риска, а сервис — за решение о дополнительной проверке.

Если модель недоступна, сервис выдаёт явную ошибку и не возвращает ложный успешный результат.

## 6. Тестовые данные и результаты

Использованы синтетические данные оборудования без персональных сведений.

| Тест | Вход | Ожидаемое поведение |
|---|---|---|
| Нормальный | 55°C, вибрация 1, 1000 ч, 0 ошибок | NORMAL |
| Высокий риск | 110°C, вибрация 8, 5000 ч, 30 ошибок | CRITICAL_RISK |
| Неверный вход | температура 300°C | ValidationError |
| Недоступная модель | available=false | RuntimeError |
| Пограничный | 90°C, вибрация 5, 2000 ч, 10 ошибок | ручная проверка |

Команда запуска: python -m pytest -q.

В наборе пять независимых тестов: корректный результат, другое поведение на высоком риске, ошибка входа, ошибка недоступной модели и сценарий ручной проверки.

## 7. Ограничения

1. Baseline не является обученной промышленной ML-моделью.
2. Risk score не является калиброванной вероятностью отказа.
3. Нет model registry и внешнего хранилища артефактов.
4. REST API, Docker и CI/CD специально для ЛР3 не добавляются, так как относятся к последующим работам.
5. Качество предсказаний требует отдельной проверки на реальном размеченном наборе данных.

## 8. Изменения относительно ЛР2

Основная архитектура сохранена. Добавлено явное разделение ответственности:

- schemas.py — контракт;
- preprocessing.py — подготовка;
- inference.py — AI-функция;
- service.py — прикладное правило;
- tests/test_component.py — автономные тесты.

По сравнению с упрощённым ModelLoader ЛР2 в ЛР3 недоступность AI-зависимости моделируется явно и приводит к ошибке, а результат baseline сопровождается версией алгоритма.

## 9. Дальнейшее развитие

В следующих лабораторных работах компонент можно подключить к воспроизводимому конвейеру данных, контейнеру, CI/CD и REST API. Для production-варианта следует заменить baseline на версионированную обученную модель, добавить контроль качества данных и мониторинг drift.

## 10. Вывод

Цель работы достигнута: реализован изолированный программный AI-компонент системы Predictive Maintenance, определены входной и выходной контракты, разделены подготовка, инференс и прикладное правило, добавлены проверки обычного, ошибочного, пограничного сценариев и недоступной модели.
